# 方案：只在缓存冷的时候切换模型

状态：已在 0.4.0 实现，未提交。实现时和方案有两处不同：
- `forkMaxTokens` 没做成配置项，改成代码里的常量 `FORK_MAX_TOKENS = 30000`，少一个要用户理解的选项；fork 仍要先打开 `forkFallback`（默认关）。
- 实现后又简化了一次：最低用到 Sonnet（`claude.floor`），本地规则只升不降，冷点之间只有说法明确的规则（评审 / 查根因、架构 / 设计）才能升档。原因是日志里 61% 的轮次小模型没分出类别，换模型最多省约 28%（Opus 和 Sonnet 读缓存一个价），而读写缓存占了八成花费，省额度的大头在上下文大小。为此报告和面板加了“花费构成”，长对话隔久回来时提示一次，上下文提醒提前到 20 万 / 40 万。
- 报告主指标仍是每会话花费（按 API 价折算的美元）。订阅额度大体按模型单价加权扣，换小模型省额度主要体现在单价上，只看缓存读取量和上下文大小反映不出来。上下文大小、7 天额度变化原来就在报告里，这次加了“冷点”“本地规则”两行。

## 为什么改

目标是在质量不变的前提下少用 Claude 订阅额度。现在的做法是每轮都分类、需要时切换模型，实测下来是亏的：

- 上周净亏 $3.90：换小模型省了 $5.55，分类花了 $4.85，换模型后缓存重写花了 $4.60。
- 全部日志（37 个会话、255 轮主对话）：
  - 缓存读取 383M token，缓存写入 9.4M token。读取量是写入量的 40 倍，额度的大头是每轮重复读上下文。
  - 真正切换模型的只有 12 轮，但每一轮都在分类。所以亏损主要来自分类，不是来自切换本身。
  - 有 62 轮（24%）落在缓存本来就冷的时刻：会话第一条消息、距上一轮超过 1 小时、上下文被压缩之后。这些时刻缓存写入了 4.9M，占全部写入的一半多。

结论：只在缓存冷的时刻分类和切换。换模型不会再多出缓存重写的花费，分类次数降到大约四分之一，平时的轮次一分钱不花。

## 怎么做

### 1. 什么叫“冷点”

满足任一条件，这一轮就是冷点：

| 条件 | 怎么判断 |
|---|---|
| 会话第一条消息 | 本会话还没有主对话的轮次 |
| 距上一轮太久，缓存已过期 | 距上一轮主对话超过 `claude.coldGapMinutes`，默认 60 分钟（缓存有效期 1 小时；用 API key、缓存有效期 5 分钟的用户改成 5） |
| 上下文刚被压缩 | `session.compact` 事件之后的第一轮；或者上下文比上一轮少了三分之一以上，用来兜住没收到事件的情况 |

### 2. 冷点做什么

1. 分类按这个顺序试，前一种失败才试下一种：
   1. `$.model.classify`（几乎不花钱，被限流时进冷却）。
   2. 本地规则（调好的那版，覆盖 38%，与模型分类一致率 85%）。
   3. fork：只在上下文小于 30K 时用。会话开头和压缩之后上下文都小，fork 便宜；上下文大时不用，因为 fork 要把整段上下文读一遍。
   4. 都不行就保持当前模型。
2. 按分类结果直接定下这一段对话的模型。冷点不需要“连续 N 轮更轻才降档”，因为降档没有缓存代价。

### 3. 冷点之间做什么

- 不分类，不降档。日志照记，状态栏显示“本段：Sonnet（冷点定的）”。
- 只保留一种升档：用户在纠正上一轮时（现有的“纠正就升一档”），立刻升一档。宁可多花一次缓存重写，也不能让质量掉下去。
- 外派提示（pi 角色）改用本地规则判断，不再依赖分类。规则判不出就不提示。

### 4. 配置

| 配置项 | 默认 | 说明 |
|---|---|---|
| `claude.switchAt` | `"cold"` | `"cold"` 只在冷点切换；`"turn"` 是现在的每轮切换，留作对照 |
| `claude.coldGapMinutes` | `60` | 隔多久算缓存过期 |

`downgradeAfter` 和 `keepAboveTokens` 在 `cold` 模式下不再生效，配置说明里写清楚。

### 5. 记录和报告

- 每轮日志加 `cold`，记下冷点原因（`start` / `gap` / `compact`），不是冷点就不写。
- 报告主指标改成接近额度的口径，美元降为参考：
  - 主对话每轮平均缓存读取量；
  - 平均上下文大小；
  - 7 天额度百分比的变化（`wk`）。
- 报告和面板加一行“冷点 N 轮 / 共 M 轮，冷点切换 K 次，冷点之间升档 J 次”。
- 对照实验不变：对照组只记下本来会选什么，不切换。版本升到 0.4.0，按新版本单独统计，不和旧数据混在一起比。

### 6. 收拾这两天没提交的改动

- `hooks/rules.ts`：换成调好的那版规则，并补上测试。
- 分类子代理（`registerClassifier`、`askClassifier`，以及 `agent.offer` 和 `turn.complete` 里的相关处理）：在自动权限模式下起不来，全部删掉。自检里那一项也删掉。
- 冷却退避、分类失败率、返工统计、日志分段这些照留。

## 预期效果和代价

- 分类：从每轮都分类，降到只在约 24% 的轮次分类；fork 只在上下文小时用。按上周的量，分类花费从 $4.85 降到 $1 以下（估算）。
- 缓存重写：降档只发生在冷点，不再额外重写。纠正时的升档照旧会重写。
- 代价：同一段对话里，后面的任务就算变轻了也不会降档，换小模型省下的钱会比上周的 $5.55 少。具体少多少，要看新版本跑一周的数据。
- 风险：一段对话以闲聊开头（比如“你好”），被定成 Haiku，接着来了难题。兜底有两层：用户纠正时立刻升档；规则判出难题、设计、评审这几类时也允许当场升档。
